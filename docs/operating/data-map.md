# The data map — every file the tool writes, and what losing it costs

This tool writes to exactly six places, and one of them is outside the repo. The point of this page is
that you can answer two questions for every one of them without reading code: **what can I safely
delete**, and **what happens if I lose this**.

The short version, and it is the only rule you have to remember:

> **`data/runs/` is disposable. `data/corpus/` is not.** Everything in `runs/` is plumbing for one run
> and is regenerated by the next one. `corpus/` is a month of model judgments that cost real money and
> cannot be recreated from anything still on disk — the postings they were made about have expired.
> `rm -rf data/runs/*` is a safe cleanup. `rm -rf data/*` is not.

Nothing under `data/`, `matches/` or `applications/` is tracked in git, so git will not save you from
the second command. `profile/` and `config/` **are** tracked, which is the whole reason a hand-tuned
rubric is recoverable and a corpus is not.

Directory creation is automatic: `triage/config.py` makes all six repo-side directories on import, so a
fresh clone that has never run anything still has somewhere to write.

## 2. What can I delete

Answers, in the order you would ask them.

**"I want the disk back."**

```bash
rm -rf data/runs/*            # safe between runs. ~40 MB here.
rm -f  data/corpus/index.json # safe always. 20 MB. Rebuilt on the next run's phase 1, ~40 s.
rm -rf data/research/*        # safe always. Company briefs re-research on demand.
```

That is 60 of the 69 MB under `data/`, and none of it is a judgment.

**"Can I delete `data/runs/` right now?"** Yes, unless a run is *in flight* or you are between phase 1
and phase 3. Three files in there are a handoff rather than an artifact: `latest-run.txt` is how
`--merge` finds the run it is merging into, `browser-jds-<run-id>.json` is what the agent's browser step
leaves for phase 3, and `archive-<run-id>.txt` is the list of mail that has not been archived yet.
Delete those mid-workflow and phase 3 fails with `no latest-run.txt — run Phase 1 first`, or you lose an
inbox cleanup. The moment the workflow is finished, all of it is junk.

**"Can I delete `data/corpus/`?"** No, and this is the one that has no undo. The state files are every
judgment the analyzer has ever made — 1,305 records here, at roughly one Opus call each. You cannot
re-derive them: the postings they describe have expired, the boards have moved on, and the mail was
archived. Concretely, losing `corpus/` costs you

* **precedent** — the retrieval index is built from these files, so scoring drops back to the rubric
  alone and every correction you made by scoring a job stops propagating. That is stage 2's entire
  feature, silently off.
* **`research/history`** — `/research-company` answers "have I seen this company before?" out of the
  same state files, so it starts answering *no* about companies you rejected last month.
* **the market retrospective** — `python -m research.market`'s first-party half *is* the corpus.
  Part 1 renders empty.

`seen.json` and `applied.json` sit in the same directory but are a lighter loss: `seen.json` costs one
re-scoring of everything inside the window (money and wall-clock, not information — dedup means you get
no duplicate output), and `applied.json` is rebuilt by re-running `/sync-applied` against your sheet.

**"Can I delete `data/reports/`?"** The `market-report-*.md` files yes, the `ba-*.json` files yes — and
the **`market-numbers-*.json` files no.** Those are a dated series and the trend section is gated on
having at least 3 snapshots spanning at least 60 days (`research/snapshots.py` · `MIN_SNAPSHOTS`,
`MIN_DAYS`). Deleting them resets that clock, and re-running the report today cannot recreate a snapshot
of what your corpus looked like in May.

**"Can I delete `matches/` and `applications/`?"** They are gitignored and the tool never reads them,
so nothing breaks — but nothing regenerates them either. `matches/<date>.md` is the curated apply doc an
agent wrote from a worklist that may itself be gone, and `applications/` holds the tailored CV you
actually sent. Treat them as documents, not as cache. If you want them backed up, they are the two
directories to point a backup at, because git is not doing it.

**"Can I delete `profile/`?"** It is tracked, so `git checkout` brings it back — which is precisely why
it is tracked. Losing an unrecorded rubric edit is the unrecoverable case, and it is the reason
`profile/` is in git even though `.gitignore` covers everything else you would expect to sit beside it.

**"Can I delete `~/.cache/fastembed/`?"** Yes. The next embed re-downloads the `bge-small-en-v1.5` ONNX
weights (~64 MB, once, from Hugging Face) and everything after that is offline again. Until it does,
retrieval degrades rather than failing: `triage/precedent.index()` logs *"scoring without precedent"*
and the run continues.

## 3. The retention story, per directory

**`data/corpus/` — permanent.** One state file per run, named by run id, so a later run never overwrites
an earlier one. Nothing prunes them and nothing should: the corpus getting longer is the tool getting
better, and 1,305 records is 8 MB. `index.json` is the one file here that is a cache; it is incremental,
so a morning that added one run embeds that run only.

**`data/runs/` — one run.** Everything is keyed by run id and nothing is ever read after the workflow
that produced it finishes. This is the directory that grows without bound and the only one worth a
periodic `rm`.

**`data/research/` — 14 days.** `research/cache.py` · `MAX_AGE_DAYS` is a freshness window, not an
eviction policy: a brief older than 14 days is **re-fetched** rather than served stale, and the stale
file is overwritten. So the directory converges on one file per company you have ever looked up, a few
KB each.

**`data/reports/` — permanent for the numbers, disposable for the rendering.** The split is deliberate
and it is documented in `docs/operating/market-report.md`: the numbers file is machine-owned and
accumulating, the markdown is a render of it, and the narrative that cites it lives in
`profile/notes/market-insights.md`, which is **hand-authored and never overwritten by anything.**

**`matches/` and `applications/` — permanent, and yours.** One file or folder per run or application.

**`profile/` and `config/` — permanent, tracked, and the only things here in git.**

## 4. Where the config actually resolves

One environment variable moves both halves of the configuration at once:

    JOBSDB_CONFIG_HOME=config/example .venv/bin/python -m triage --paste <url>

`JOBSDB_CONFIG_HOME` points `PROFILE_DIR` *and* the settings loader at one directory, so the demo reads
and writes nothing of yours. It does **not** move `data/`, `matches/` or `applications/` — those stay
repo-root-relative, so a demo run still writes its worklist and its state file into your real `data/`.
That is intentional (a demo run is a real run and its judgments are real), but it is the one asymmetry
worth knowing before you point the variable somewhere and expect full isolation.

It is also resolved against the current working directory (`Path(raw).resolve()`), so a **relative**
value in a scheduled job resolves against whatever cwd the scheduler gave you. Use an absolute path
there — `docs/operating/scheduling.md` says the same thing from the other side.

## 5. Backup, in one line

Everything that matters and is not in git: **`data/corpus/`, `data/reports/market-numbers-*.json`,
`matches/`, `applications/`, and `.env`.** That is under 10 MB excluding the index you should not bother
backing up. Everything else on this page is either tracked, derived, or junk.
